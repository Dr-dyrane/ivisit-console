# 01 — Schema & Drift (Backend Research)

> **Scope.** Read-only research over the shared Supabase schema owned by `ivisit-app`. This doc
> builds the canonical table map from the pillar migrations, compares the pillars against the
> **live** database (captured via information_schema dumps in `ivisit-app`), and gives a definitive
> answer on the console audit's "missing column" questions.
>
> **Authority order for "what is actually deployed":** the live-DB dump
> `ivisit-app/docs/audit/inventory/live_schema_inventory_2026-03-02.json` (full `information_schema`
> extract, 456 columns) is the ground truth for **column existence**. The pillar migrations are the
> *intended* contract. The two diverge — see the drift table. Nothing in `ivisit-app` was modified.
>
> **Cite key:** `path:line` throughout. `app/` = `ivisit-app/`, `console/` = `ivisit-console/`.

## 2. Live table inventory (what is actually deployed)

From `docs/audit/inventory/live_schema_inventory_2026-03-02.json` (`.tables`, 40 rows) the live public
schema on **2026-03-02** contained (excluding PostGIS system tables `geography_columns`,
`geometry_columns`, `spatial_ref_sys`):

```
access_requests, admin_audit_log, ambulances, doctor_schedules, doctors, document_invites,
documents, emergency_doctor_assignments, emergency_requests, health_news, hospitals, id_mappings,
insurance_billing, insurance_policies, ivisit_main_wallet, medical_profiles, notifications,
organization_wallets, organizations, patient_wallets, payment_methods, payments, preferences,
profiles, room_pricing, search_events, search_history, service_pricing, subscribers, support_faqs,
support_tickets, trending_topics, user_activity, user_roles, user_sessions, visits, wallet_ledger
```

Two axes of drift are visible immediately:

- **Live-only tables (not in any pillar migration):** `access_requests`, `document_invites`.
  These exist in the live DB but have no `CREATE TABLE` in the pillars.
- **Pillar-only tables (absent from the 2026-03-02 live DB):** `emergency_status_transitions`,
  `emergency_chat_rooms/_participants/_messages`, `providers`, `hospital_media`,
  `hospital_import_logs`, `exchange_rates`, `emergency_contacts`, `user_sessions`(present),
  `search_selections`. These pillar tables were authored **after** the 2026-03-02 dump. The later
  **2026-06-11 probe confirms** `emergency_status_transitions` (654 rows) and the emergency-chat
  path now exist live — i.e. the migrations were applied between 03-02 and 06-11. Treat 03-02 as a
  historical low-water mark for *column* evidence and 06-11 as the current row-count/contract check.

## 3. `apply_live_fixes.sql` — what it actually changes (and does NOT)

`supabase/scripts/apply_live_fixes.sql` is described as hand-applied live parity fixes. Full structural
survey (every top-level statement):

| Block | Lines | Kind |
|---|---|---|
| ID stamping / resolver refinements | `:8-120` | `CREATE OR REPLACE FUNCTION` (`stamp_entity_display_id`, `get_entity_id`) |
| Ensure triggers active | `:123-143` | trigger (re)creation |
| Emergency status reconciliation | `:145-1077` | RPC redefs (`canonicalize_emergency_status`, `assign_ambulance_to_emergency`, `approve/decline_cash_payment`, …) |
| Logistics RPC transition patch | `:1079-1470` | RPC redefs (`discharge_patient`, `cancel_bed_reservation`, `complete_trip`, `cancel_trip`) |
| Resource reassignment closure | `:1472-1854` | RPC redefs (failover fns) |
| Doctor release / telemetry / RLS / geospatial | `:1856-2174` | RPC + RLS policy redefs |

**Definitive:** `apply_live_fixes.sql` contains **zero `CREATE TABLE`, zero `ALTER TABLE`, zero
`ADD COLUMN`, zero `ADD CONSTRAINT`**. It is a pure functions/RLS/triggers reconciliation file. It
therefore **adds none** of the console-flagged columns. (Confirmed by content search — no DDL matches.)

**One drift *introduced* by this file:** its `stamp_entity_display_id` (`:22-37`) is an **older**
variant than the pillar's — it is **missing the `viewer`→`VWR` and `sponsor`→`SPN` prefix branches**
that the pillar has (`identity:293-294`), and its resolver `get_entity_id` (`:104`) likewise omits
`VWR`/`SPN` from the profile-prefix list (pillar has them, `identity:378`). So the live function (if
this file was the last writer) lags the pillar for viewer/sponsor display-ID beautification. This is
cosmetic, not a data-shape issue.

Other hand-applied scripts in `supabase/scripts/` are data/backfill utilities, not schema DDL:
`backfill_hospital_media.js`, `cleanup_hospital_shadows.js`, `dedupe_demo_hospitals.js`,
`cleanup_duplicate_providers.sql`, `audit_duplicate_locations.sql`, `seed_platform.sql`,
`data_import_fixed.js`, subscriber add/export scripts. None add columns to the audited tables.

## 4. DRIFT TABLE — pillar vs live-fix vs live DB (audited tables)

Legend: **P** = pillar migration DDL · **F** = `apply_live_fixes.sql` · **L** = live DB
(`live_schema_inventory_2026-03-02.json` full dump unless noted). ✅ present / ❌ absent.

### `insurance_policies` — **MAJOR drift; live is a superset of the pillar**

Live has **19 columns**; pillar defines **10**. Live-only columns are additive (no pillar/live-fix owns them).

| Column | P (`finance:132-143`) | F | L (03-02) | Verdict |
|---|:--:|:--:|:--:|---|
| `id`, `user_id`, `policy_number`, `is_default`, `is_active`, `created_at`, `updated_at` | ✅ | — | ✅ | in sync |
| `provider_name` | ✅ | — | ✅ | in sync |
| `policy_type` (DEFAULT `'basic'`) | ✅ | — | ✅ | in sync (legacy) |
| `coverage_amount` | ✅ | — | ✅ | in sync (legacy) |
| **`plan_type`** | ❌ | ❌ | ✅ | **DRIFT: live-only** — console reads it (`insuranceService.js:218,220,251`) |
| **`status`** | ❌ | ❌ | ✅ | **DRIFT: live-only** |
| **`verified`** | ❌ | ❌ | ✅ | **DRIFT: live-only** — console filters `.eq('verified', …)` (`insuranceService.js:206,235-237`) |
| **`coverage_percentage`** | ❌ | ❌ | ✅ | **DRIFT: live-only** |
| **`coverage_details`** (jsonb) | ❌ | ❌ | ✅ | **DRIFT: live-only** |
| **`linked_payment_method`** | ❌ | ❌ | ✅ | **DRIFT: live-only** |
| **`starts_at` / `expires_at`** | ❌ | ❌ | ✅ | **DRIFT: live-only** |
| **`provider`** (text, in addition to `provider_name`) | ❌ | ❌ | ✅ | **DRIFT: live-only** — the 06-11 probe's contract expects `provider` and passes (`export_live_schema_inventory.js:33`) |

> Net: the live `insurance_policies` carries BOTH the pillar's legacy shape (`provider_name`,
> `policy_type`, `coverage_amount`) AND a newer shape (`provider`, `plan_type`, `status`, `verified`,
> `coverage_percentage`, `coverage_details`, `starts_at`, `expires_at`, `linked_payment_method`).
> The pillar migration was **never updated** to add the newer columns → the console is reading real
> columns; **the pillar is stale**, not the console.

### `profiles` — **no drift; pillar == live == 28 columns**

| Column | P (`identity:15-44`) | L (03-02) | Verdict |
|---|:--:|:--:|---|
| all 28 pillar columns (`id … updated_at`) | ✅ | ✅ | in sync |
| **`status`** | ❌ | ❌ | **does NOT exist** in live |
| **`suspended_at`** | ❌ | ❌ | **does NOT exist** in live |
| **`verification_status`** | ❌ | ❌ | **does NOT exist** in live |
| **`verified_at`** | ❌ | ❌ | **does NOT exist** in live |

Live `profiles` check constraints are exactly `profiles_role_check`, `profiles_provider_type_check`,
`profiles_onboarding_status_check` (03-02 dump) — matching the pillar, with none for a `status` column.

### `visits` — **reverse drift + no status CHECK anywhere**

- **`visits.status` CHECK:** live `visits` has only `visits_rating_range_chk` (03-02 constraint list);
  **there is NO `visits_status_check`**. Pillar also has none (`logistics:163` is bare
  `TEXT DEFAULT 'upcoming'`). → **Both agree: `visits.status` is unconstrained free text.** The
  console's assumption of a status CHECK is unfounded in *both* pillar and live.
- **Reverse drift (pillar ahead of 03-02 live):** live `visits` had **21 columns** on 03-02; the pillar
  defines ~40. Live was missing pillar columns incl. `hospital`,`hospital_image`,`address`,`phone`,
  `image`,`doctor`,`doctor_image`,`summary`,`preparation`,`prescriptions`,`room_number`,
  `estimated_duration`,`meeting_link`,`insurance_covered`,`next_visit`,`latitude`,`longitude`,
  `tip_amount`,`tip_currency`,`tipped_at`,`tip_payment_id`. These are later pillar additions;
  whether they are applied live now can only be re-confirmed with a fresh full dump (the 06-11 probe
  only checks `id,request_id,user_id,hospital_id,status,type,cost,created_at,updated_at` — all
  present, `export_live_schema_inventory.js:26`).

### `subscribers` — in sync (both bare `status`)
Live (9 cols) == pillar. `status TEXT DEFAULT 'active'` with **no CHECK** in both; only
`subscribers_type_check` exists live. `metadata` column present in pillar (`identity:165`) but **absent
in the 03-02 live dump** → minor drift (pillar-ahead), low impact.

### `medical_profiles` — in sync (14 cols), **no `display_id`** in either.

### `hospitals`, `organizations`, `wallet_ledger`, `payments` — no column drift found
- `hospitals`: live has `verified`,`verification_status`,`status` (03-02) — matches pillar; the
  provider-taxonomy + media columns are later pillar additions (re-verify with fresh dump).
- `wallet_ledger`, `payments`, `organization_wallets`, `patient_wallets`, `payment_methods`,
  `insurance_billing`: the **2026-06-11 probe** reports `missing_columns: []` for all against its
  contract (`live_schema_inventory_2026-06-11.json`), i.e. no drift on the probed columns.

**Bottom line for the console data-sync work:**
- `insurance_policies` — **safe to read** the newer columns (`plan_type`, `status`, `verified`,
  `coverage_percentage`, `coverage_details`, `expires_at`, `provider`); they are live. The pillar
  migration is the artifact that lies, not the DB. Recommend flagging the pillar as stale to the
  `ivisit-app` owners (do not edit it from here).
- `profiles.status/suspended_at/verification_status/verified_at` — **genuinely absent.** The console
  must either stop reading them or the app team must add them. Do not assume they exist.
- `visits.status` — **no enum/CHECK exists in the DB.** Any canonical-status work needs an app-side
  migration; the console cannot rely on DB-enforced values today.

## 6. Caveats / confidence

- Column-existence claims for `insurance_policies`, `profiles`, `visits`, `subscribers`,
  `medical_profiles` come from the **2026-03-02 full information_schema dump** — the newest *full*
  dump available in-repo. Row-count/contract confirmation for the 12 finance/logistics tables is
  **2026-06-11**. A fresh full dump would be needed to confirm whether later pillar-added `visits`/
  `hospitals` columns are now live; this doc flags those as "pillar-ahead, re-verify" rather than
  asserting them.
- `SCHEMA_SNAPSHOT.md` was explicitly **excluded** as live evidence because it is regex-generated
  from the migrations (`generate_schema_snapshot.js:18`) and cannot show drift.
- No writes were made to `ivisit-app`, the Supabase CLI was not run, and the DB was not touched.
